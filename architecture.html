The stack

Eleven layers.
Nothing borrowed.

From power-on to an interactive shell, every layer here is either Apple's own open-source Darwin code, patched to compile and boot on a modern toolchain, or a from-scratch implementation targeting the real, ground-truthed on-disk ABI. Tap any layer to open it up.

Target hardware — QEMU q35 / x86_64
qemu-system-x86_64 -machine q35 -cpu Haswell, OVMF firmware
real hardware model

Boots on -machine q35 with edk2 OVMF firmware (Homebrew's qemu package). The CPU model matters more than it looks: qemu64 fails xnu's own cpuid_set_cpufamily() vendor/family check outright ("Unsupported CPU"). -cpu Haswell is the one that satisfies it.

  • PS/2 keyboard input (i8042, ports 0x60/0x64), polled directly — no USB HID stack, per explicit scope decision.
  • Output via xnu's existing GOP-framebuffer / serial console code in pexpert — no new video driver needed.
Custom UEFI bootloader
boot/ — clang + lld-link, no gnu-efi
done

Apple's real boot.efi was never open-sourced, so this is a clean-room UEFI application: it parses the kernel's LC_SEGMENT_64 commands, loads the launchd RAMDisk into a separate AllocatePages region, hand-builds Apple's flattened device tree (every node needs an explicit "name" property — a zero-property node is an end-of-list sentinel, not "no properties"), fills in the 4096-byte boot_args struct, and calls ExitBootServices.

  • Strips every EFI_MEMORY_RUNTIME descriptor before exit — this project never calls SetVirtualAddressMap(), and leaving them in let two OVMF regions collide at virtual page 0, clobbering the low identity map.
  • Bump-allocates boot_args/device-tree/memory-map immediately after the kernel's own Mach-O segments and reports them as part of ksize, so xnu never frees or reuses that memory.
XNU kernel — Mach + BSD
src/xnu · xnu-6153.141.1 · 14+ source patches
done

The real, unmodified-in-spirit Apple kernel — fork, execve, waitpid, signals, the scheduler, VM/copy-on-write, mmap, all stock bsd/kern and osfmk code. Patched only where a modern toolchain forces it.

  • The deep one: osfmk/x86_64/start.s loaded absolute addresses of high-canonical-but-physically-low symbols truncated to 32 bits — a long-standing xnu idiom for pre-paging code. Modern ld now hard-rejects that. Fixed at 9 call sites (including one direct far-jump with no relative form) using only relocation kinds the linker still accepts.
  • NFS, netboot, and the Python-2-only lldbmacros install step compiled out — out of scope, not broken.
  • Real upstream bugs fixed along the way: undefined PCI-config identifiers in cpuid.h, a missing comma silently concatenating two malloc-zone name strings.
fat16lite — root filesystem driver
bsd/miscfs/fat16lite · from scratch, read + write
done

Replaced an earlier MOCKFS + in-memory RAMDisk design (a 3-node read-only "boot from an executable" filesystem) once real directories, multiple binaries, and file creation were needed. Full VFS vnops: mkdir/create/write/remove/rmdir, plus cluster allocation and FAT-entry management, written from scratch.

  • Root-mount flags were hardcoded to MNT_RDONLY deep in vfs_subr.c, silently overriding the filesystem's own writable flag.
  • Repeated in-place overwrites during image deployment fragmented cluster runs; the driver assumed contiguous clusters, mapping later pages to the wrong physical memory. Fixed by defragmenting on every deploy, not patching around it.
dyld — the dynamic linker
userland/dyld/ · from scratch
done

Loads LC_LOAD_DYLIB dependencies from disk, rebases (REBASE_OPCODE_*), binds (BIND_OPCODE_*, eager and a real lazy dyld_stub_binder path), and resolves symbols via the export trie — all interpreted against the real mach-o/loader.h. The kernel's own load_dylinker() needed zero changes.

  • xnu ASLR-slides the dylinker itself, unconditionally — so dyld has to be genuine position-independent code, correct at any load address with zero fixups of its own. Needs both -fPIC and explicit hidden visibility on every cross-TU extern, or clang routes them through a GOT slot only a rebase pass (which dyld can never apply to itself) would populate.
  • Known v1 limits: fixed 256MB dylib slots instead of a real VM allocator, no @rpath, no two-level namespace.
libSystem.B.dylib
userland/libSystem/ · 568 exported symbols
done

Every userland/libc/ source file, recompiled -fPIC and linked -dynamiclib — the same from-scratch, raw-syscall libc that BusyBox already ran against statically, now shared. __libc_start had to move to a small per-executable object (libc_start.o) since ld64's mod-init-func section symbols are scoped per final image, matching real Darwin's crt1.o/libSystem split.

  • Static linking remains the default for anything that doesn't need a shared dependency — BusyBox/coreutils were deliberately not migrated, to protect the already-verified boot path.
libobjc.A.dylib — Objective-C runtime
userland/libobjc/ · genuine nonfragile ABI2
done

class_t/class_ro_t/method_t/ivar_t/category_t/protocol_t metadata layout ground-truthed field-by-field against otool output on real compiled .m probes — real, unmodified .m source compiles and runs against it. Hand-written x86_64 objc_msgSend with a per-class dispatch cache.

  • Class realization was silently broken until a tagged-pointer scheme distinguished "still the compiler's read-only class_ro_t" from "already realized" — data is never NULL, so the naive guard was true on every class's first call.
  • ARC's objc_retainAutoreleasedReturnValue fast path turned out to be semantically required, not an optimization — found via a live double-free.
CoreFoundation
libCoreFoundation.dylib · pure C, no libobjc dependency
done

Real CFRetain/CFRelease refcounting and a real CFRuntimeClass registration table, with CFString, CFArray, CFDictionary, CFSet, CFNumber, CFBoolean, CFData all genuinely callback-driven.

  • v1 storage tradeoffs, documented not hidden: CFString is UTF-8-backed (BMP-only UniChar decoding), and CFDictionary/CFSet are linear arrays — O(n) lookup, not a hash table.
  • No CFRunLoop yet — everything here is synchronous, run-to-completion.
Foundation
libFoundation.dylib · real toll-free bridging
done

CFRuntimeBase now opens with a literal void *isa matching libobjc's objc_object layout, so a bridged CFStringRef cast to id is a genuinely dispatchable object — NSCFString forwards -retain/-release/-hash/-isEqual: straight into the matching CF calls. Retain counts and equality are identical through either API.

  • NSException uses real historical NS_DURING/NS_HANDLER macros (setjmp/longjmp) instead of modern @try/@catch — this tree has no zero-cost DWARF unwinder for x86_64.
  • Chasing NSUserDefaults's disk persistence surfaced three real fat16lite bugs, none of them Foundation's — documented in the roadmap.
libdispatch — Grand Central Dispatch
libdispatch.dylib · built on real kernel-scheduled pthreads
done

Serial and concurrent dispatch_queue_t, dispatch_async/sync, dispatch_once, semaphores, groups, and dispatch_after — on top of Phase 16's real bsdthread_create-backed pthreads, not xnu's actual workqueue/kevent machinery.

  • A serial queue's drainer holds the queue for its entire backlog, not one item at a time — a concurrent dispatch_async mid-drain just sees the gate and skips scheduling a duplicate wakeup.
  • No dispatch_source_t yet (needs kevent, unwired); dispatch_get_main_queue() is an ordinary auto-draining queue, not runloop-attached.
launchd (PID 1) + BusyBox userland
userland/launchd/ · real upstream BusyBox 1.36.1
done

Real PID 1, loaded by xnu's own load_init_program() — which already tries /sbin/launchd before /sbin/init, so this needed zero kernel changes. A hand-written recursive-descent XML plist parser drives daemon supervision: RunAtLoad, throttled KeepAlive respawn, orphan reaping via wait4(-1, …), and a bounded SIGTERM → reboot(RB_HALT) shutdown.

The interactive shell is genuine, unmodified upstream BusyBox 1.36.1 (ash), statically linked against the raw-syscall libc — no dyld dependency for the base coreutils, by design.

Ground-truthed, not guessed

The boot protocol, bit for bit

Every field below was read out of pexpert/pexpert/i386/boot.h and real xnu source before being implemented — not assumed from documentation that doesn't exist for this era.

boot_args

Exactly 4096 bytes (kBootArgsVersion2). Revision/version/flags, a 1024-byte command line, the EFI memory map descriptor, video framebuffer info, the device-tree physical address + length, and the kernel's kaddr/ksize.

Flattened device tree

Apple's own format: each node is {nProperties, nChildren} followed by that many name/length/value property records, then children depth-first. A zero-property node is an unreachable dead end, not "empty" — /chosen/memory-map's "RAMDisk" property is how the kernel finds its root device.

Syscall ABI

BSD class-2 syscalls: 0x2000000 | number in %rax, args in %rdi,%rsi,%rdx,%r10,%r8,%r9, error signaled by the carry flag with a positive errno left in %rax — never negated. Missing the carry check was the single bug that unblocked the most downstream debugging in this project.

Why it's built this way

Deliberate scope, documented in the open

Every deviation from "just port real macOS" was a decision with a reason, not a shortcut taken quietly.

No AHCI, no HFS+

Apple's real AHCI/NVMe and HFS+ kexts were never open-sourced. Writing a disk driver from scratch was a real option — ravynOS spent roughly six months on exactly that — but it's out of scope for the smallest system that can boot to a real shell. The root filesystem is a from-scratch FAT16 driver instead.

PS/2, not USB

Keyboard input polls the i8042 controller (ports 0x60/0x64) directly. QEMU's q35 machine includes one by default, and a USB HID stack buys nothing this project needs yet.

MOCKFS → FAT16

The original plan was a 3-node read-only MOCKFS backed by an in-memory RAMDisk — the smallest possible root filesystem, needing zero drivers. It couldn't support BusyBox's separate applet binary, real directories, or mkdir/echo >, so it was replaced outright once those became the goal.

Static libc first, dyld later

The original decision was "no dyld at all" — a statically-linked Mach-O with no LC_LOAD_DYLINKER needs no dynamic-linking runtime at all, and building real dyld + Libsystem + objc4 is a multi-month undertaking on its own. That constraint was later revisited on purpose, once a real dyld became the more interesting problem — see the roadmap for Phase 11.
